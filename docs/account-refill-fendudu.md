# 粉嘟嘟手动补号

账号管理页在“手动补号”右侧增加“粉嘟嘟手动补号”。点击后进入同一补号弹窗的粉嘟嘟页签。它只用于管理员主动购买，不改变现有自动补号号商，也不自动切换号商。

两个入口固定打开各自的号商页签。待确认请求按号商和分组分别保存，恢复请求不会覆盖刚选择的入口；旧版浏览器会话中的请求会保留到对应号商下。普通购买、强制购买和原单重试均标明目标号商，切换号商不会修改原请求的编号、套餐或强制标记。仅清除已确认或明确拒绝的对应请求，另一号商的待确认请求继续保留。

## 配置与使用

1. 在粉嘟嘟网站配置指向**当前 SUB2 实例**的 SUB2 推送连接。连接管理由号商网站提供。
2. 打开“粉嘟嘟手动补号”，选择现有补号规则分组，在“粉嘟嘟连接设置”中保存 API 对接码和推送连接 ID。留空连接 ID 使用号商默认连接；显式填写连接 ID 可以在交付时校验该连接。
3. 已保存的对接码不会回显，留空对接码可保留原值。配置和在途订单按规则存储；新分组只继承连接，不复制任务、预算或推送规则。
4. 在原“推送设置”中确认分组、并发、代理、到期时间等并保存。返回粉嘟嘟页签，选择 Pro5x 或 Pro20x，点击“补入 1 个账号（扣 1 次）”。
5. 在“消费与进度”中跟踪原订单。粉嘟嘟公开 API 不提供凭据 JSON 下载；账号交付后可使用系统现有的账号导出功能。

手动提交后会进入“消费与进度”，每笔粉嘟嘟订单直接显示号商回收时间；尚未取得时显示“等待号商返回，自动同步中”。此处只显示号商返回的原生时间，不把本地保留时间或 100 分钟兜底当成号商确认时间。账号列表继续分别显示号商回收时间与实际到期时间。

每次点击仍沿用现有手动补号入口的规则：配置版本检查、请求去重、推送开关、分组和代理校验、在途限制、每日数量限制，以及强制补号的原有语义。每个订单保存提交时的推送设置；后续改设置不会改写已提交任务。关闭自动购买或监测不妨碍已接受的手动任务继续交付。

实际导入共用现有设置构造和启用逻辑，包括分套餐并发、绑定分组、代理策略、优先级、负载因子、倍率、Privacy、WS、指纹、命名/备注、模型映射、调度状态和过期保留策略。

## 号商协议与差异

- 文档：<https://gpt.20251231.xyz/my/api#key>
- 固定 API 地址：`https://gpt.20251231.xyz/open-api/revoke/my`
- 鉴权：`X-Api-Key`，不会跟随重定向转发凭证。
- `GET /products` 查询套餐剩余次数及可下单状态。
- `POST /order` 每单 `count=1`，使用发送前已保存的本地任务 UUID 作为 `request_id`，同时发送套餐、连接和保存的分组；关闭号商的订阅自动调度和备用连接切换。积分功能启用后，即使使用旧次数，也必须携带 16～128 字符的请求编号。
- `GET /cycle-detail?id=...` 查询原订单；`GET /cycles` 按游标分页核对丢失回执的原订单。HTTP 200 仍需校验业务成功字段。

粉嘟嘟消耗**预购次数**，没有原号商的积分报价。界面按 1 次预购次数显示；订单占用共用的每日数量，但积分记为 0，不虚构积分换算。下单前扣除相同对接码在其他规则中尚未取得订单 ID 的本地预占。次数快照每五分钟刷新，成功取得订单 ID 后的下一轮工作循环会更新；“同步余额、租期与规则”可立即查询次数，且不受原号商退避影响。

粉嘟嘟先向配置的 SUB2 推号，本服务随后查询订单并接管该账号，不重复创建账号。接管前核对订单编号、套餐、连接、下单时间和本地账号的 ID、邮箱、OAuth 类型及创建时间。推送设置、代理分配、租期元数据和恢复标记在同一数据库事务中提交，再按保存的状态启用。

**交付窗口：** 号商刚推入账号到本服务完成查询接管之间，账号可能短暂使用号商连接的默认设置。号商默认设置应与目标规则相符；本集成不能保证第三方初次推送与本地设置应用原子完成。暂停推送后，已在途的号商订单仍可能推入账号；本服务发现后将其停用，恢复时继续应用原任务。

粉嘟嘟的“号商回收时间”优先使用 API 返回的 **`revoke_at`**，没有有效值时使用 **`deadline_at`**；只有两者都没有有效值，首次导入才使用账号创建时间加 100 分钟兜底。后续同步若仍缺字段，保留已记录的租期；若 API 返回原生时间，则更新为原生租期，不受 100 分钟上限限制。随后沿用现有规则：有更早的固定截止时间时先截短，再叠加保留时间；同步尊重管理员手动设定的本地到期时间。例如 API 回收时间 11:16:37、保留 10 分钟，本地到期通常为 11:26:37。此集成读取号商时间，不修改号商实际执行的回收任务。

## 不确定订单的恢复

新版公开文档支持 `request_id` 幂等：同一次购买必须复用编号和完整参数，新购买才生成新编号。实现使用持久化任务 UUID 和该任务保存的推送设置，不在发送时生成编号。POST 前仍先持久化提交标记，每个本地任务最多提交一次；超时、响应丢失、格式异常或提交后进程退出都继续只读核对。升级前没有发送请求编号的旧任务也不会补发 POST。

- 明确的业务拒绝（`success=false`、没有已创建订单、没有 `pending`，且返回具体错误）结束为失败并释放本地预占；HTTP 400/401/402/403/422 的完整拒绝回执同样处理。每日次数仍计入本次尝试，不自动重新购买。缺失 `success`、矛盾回执、限流、冲突或服务错误继续保留原任务核对，不能据此推定未扣费。
- 返回唯一 `cycle_ids` 时直接跟踪原订单，不要求 `created` 一定是 1；重复请求的已有订单、`pending=true` 的已有订单都不当作新增购买。没有订单 ID 的 `pending=true` 保持处理中，继续只读核对。只有确认账号实际推送并应用设置后才标记导入成功。
- 下单响应的 `error`、`warning` 和非 2xx JSON 错误经脱敏、长度限制后显示在原任务的号商说明中；不回显 API Key。原订单成功恢复关联后清除旧的回执错误。

- 已取得订单 ID：持续查询原订单；交付失败时“重试原任务”继续处理原账号。
- 未取得订单 ID：后台自动只读查询订单列表，完整核对下单时间窗口中的候选订单。只有套餐、连接、时间、本地账号身份唯一匹配，且无其他分组竞争认领时才自动恢复；多笔候选、分页不完整或身份不符时继续待核对，不重复下单。也可将人工核对的原订单 ID 填入“消费与进度”。
- 已唯一确认原订单但仍等待推送时，每 15 秒继续核对，并提前展示号商已经返回的回收时间；网络错误、限流和不确定匹配仍沿用退避规则。
- 普通账号编辑及凭据刷新保留已提交的补号关联。旧版本丢失关联的已交付账号，在订单、连接、账号 ID、邮箱及创建时间重新验证后恢复租期同步；不重新导入、不分配代理、不重新启用，保留手动截止时间。粉嘟嘟使用独立轮转位置，每轮至多核对两笔，避免被主号商的旧订单挤占同步机会。关闭自动监测或主号商退避时，已交付的手动订单仍每五分钟参与租期核对。
- 核对时原订单已交付并关闭，或交付租期已过：补齐原账号关联和时间记录，结束待核对任务，保持停用；不分配新代理、不重新购买。保留管理员设定的更早截止时间。已关联的过期交付也可同步原生回收时间，但不会重新启用。
- 超时提醒发送前再核对最新状态；已交付或已结束的任务不发送旧提醒。机器人失败后排队的提醒也会去掉已解决任务，真正未完成的任务仍正常提醒。
- 粉嘟嘟、原手动补号和自动补号共用“补号进度通知”：开始、确认失败、成功导入均通知，满 5 分钟未导入每单提醒一次。后续成功仍发成功通知；两种提醒统一显示套餐、分组和原号商订单编号；尚未取得编号时明确提示，不拿本地编号冒充，使用现有机器人与去重规则。5 分钟提醒在本轮交付处理后判定，已导入等待启用的账号不会误报未导入。可配置的超时保底通知仍沿用其独立开关及自动补号规则。
- 确认号商没有受理：使用现有“确认未受理”操作释放任务后，才重新提交。
- `order_stopped`：号商明确说明未扣次数，任务终止且不会触发自动重新购买。其他失败或未知状态继续保留原订单供核对，不能据此推定退款成功。

有在途粉嘟嘟订单时禁止更换该规则的对接码或连接。不要通过删除任务、更换对接码或修改持久化状态来绕过核对。

## 发布与验证边界

粉嘟嘟的状态保存在现有补号配置中。同批发布的账号累计统计通过 `258_account_lifetime_stats.sql` 新建汇总表和触发器。先将**所有执行补号的实例**升级到支持 `provider=fendudu` 的版本，再首次使用按钮。旧版本不识别新号商和多定时任务字段，不能与新版本混跑，也不能带着在途粉嘟嘟任务直接回滚旧版本。回滚前应先处理全部在途任务并保留配置备份。

对接码使用现有 SecretEncryptor 加密，返回视图不含密文、哈希或明文；审计请求体中的 `api_token` 由现有 token 键脱敏规则处理。不得把对接码放入源码、浏览器持久缓存、截图或发布说明。

本次验证包含：真实 API 的只读鉴权/产品/历史订单查询、Go 补号回归、断线与进程恢复、跨组预占、暂停恢复、租期同步、HTTP 业务失败/重定向测试，以及前端类型检查、弹窗/i18n 测试、生产构建和 1440/390 宽度浏览器检查。浏览器验证使用本地接口替身并拒绝写请求。账号接管方法通过数据库事务替身验证了凭据保留、代理选择、配置应用、恢复去重和失败回滚边界。

未执行真实付费下单；新增账号接管方法使用事务替身验证。上述测试不能代替实际交付验收。

## 多定时任务与账号统计

补号规则最多保存 20 条每日任务，每条可单独启停、设置北京时间、1–100 个数量，以及 Pro5x、Pro20x 或跟随当前套餐轮转。旧单任务保留时间、数量与执行记录。每条任务独立保存每日收据，编辑和重启不重复扣费；预算和推送策略仍共用当前分组规则。明确指定套餐的任务不推进自动轮转位置。

账号管理的列选择新增默认隐藏的“账号统计”，指标与“今日统计”一致：请求、Token、账号费用、标准费用及用户费用。每个存活账号仅保存一行累计汇总，不复制请求明细或凭据。首次升级从尚存的请求日志回填，已被清理的历史明细无法恢复；此后日志清理不重置累计值。软删除、批量删除或物理删除账号时清理累计行，并阻止晚到请求重新生成已删账号的累计数据。

多任务的套餐隔离、重启去重、旧配置迁移、删除与过期客户端行为有 Go/Vue 回归覆盖；统计回填、幂等、费用修正、请求去重、明细保留周期和并发删除通过 PostgreSQL 集成验证。
