# 558669 补号渠道

管理员在账号列表打开 **558669 补号**，填写 API Key，选择“验证并保存 558669 密钥”。验证仅调用 `/catalog`，不下单。连接信息按补号分组保存；未创建的分组可以继承已配置的连接，但不会继承订单或预算使用量。

## 手动补号

手动入口可选择 1208、Muze 或 558669。558669 的 Pro100 对应 `pro5x`，Pro200 对应 `pro20x`，默认 Pro200。沿用该分组已保存的投递分组、代理、IPv6、并发和租期策略。手动订单只使用所选渠道，不自动购买备用渠道的账号。

页面展示报价、报价版本、服务条款、可用积分和号商预占积分。不可用套餐显示原因。密钥单独加密保存，不写入前端存储或审计请求体。

## 自动补号与备用渠道

在“补号规则”选择主渠道和备用渠道，打开备用补号开关并设置失败次数。轮转步骤也支持 558669。旧规则保持 1208 和 Muze 互备；显式选择后按所选备用渠道执行。某个轮转步骤与备用渠道相同时不再降级。

558669 使用独立的单价上限和每日积分预算；三个渠道共享当前规则的每日订单数量上限。积分直接使用 `/catalog` 的单位，不乘除 100，也不折算 Muze 预购次数。每日定时任务同样支持该渠道，整批余额和预算不足时不创建部分订单。

主渠道确认失败达到阈值，或持续确认套餐关闭、缺货、余额不足时，才会按现有需求创建一个备用 Pro20x 订单（558669 对应 Pro200）。订单之间保存承接关系，避免重复降级。

558669 的超时、503、未知状态和 `review` 不触发超时重购或跨渠道降级。有任务编号继续查询原任务；没有编号时使用原幂等键、原套餐和原报价版本重试。已提交请求不会因报价刷新而改变内容。409 保留原任务并按原因核对；不通过新幂等键自动绕过。

## 交付与凭据更新

创建请求前重新读取报价，并在首次 POST 前持久化所用报价版本和幂等键。响应必须匹配原服务、套餐、格式、数量、价格、报价版本和任务编号。

`result_ready=true` 时尝试领取；权益仍在确认中也可以交付。若交付接口返回 409，则继续核对原任务，至少等待 120 秒；410 表示交付已过期。429 遵守 `Retry-After`，只暂停 558669。

导入后每 120 秒核对权益和凭据版本；权益确认后改为每 5 分钟核对，直至租期结束。`delivery_version` 增加时重新下载同一任务的 JSON，验证邮箱、账号身份和原订单标记，在同一数据库事务中更新凭据与版本标记。不会再次创建账号、分配代理、覆盖分组和状态或从下载时间重新计算租期。进度表分别展示交付、权益、计费状态与已应用的凭据版本。
