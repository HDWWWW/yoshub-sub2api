# 账号补号与快乐首字分组设置

分组可选择 1208 或 Muze 为主号商。手动入口、备用切换及预计回收时间见[号商补号说明](account-refill-muze.md)。

本版本通过号商公开 API 实现截图可确认的规则和设置。服务商内部未公开的算法不作为实现依据。

## 分组规则与套餐轮转

补号面板顶部选择当前分组。各组分别保存开关、补号方式、监测阈值、时间窗口、预算、冷却、在途上限、推送设置、通知和订单记录。切换分组前须保存修改。原规则和在途订单保留；新规则默认关闭自动购买，只继承原规则的连接信息，保存后可独立更换 Key。跨组投递的在途订单会抵扣目标分组缺口；同一号商钱包的本地待提交预占也会合并核对。

在“补号规则”开启套餐轮转，添加 1–20 个有序步骤，每步可连续下单 1–100 个。例如 `Pro20x × 1 → Pro5x × 2` 会持续按 `20x、5x、5x、20x……` 自动下单。轮转与容量、固定储备、定时模式组合使用，每笔仍遵守触发条件、冷却、单价上限和本组预算。套餐不可用或预算不足时等待，不跳过当前轮次。

轮转位置与订单、预算预占在同一次持久化中保存；重启接续，网络失败重试仍用原幂等键和套餐，不重复占轮次。手动补号不推进轮转。新自动订单预留一个轮次，确认失败后该轮次仍未完成：保留原套餐，后续有需求时优先重补，不因一次“储备充足”或健康上限判断丢失。调整顺序、数量或开关会重新开始轮转并取消旧轮次重补；调整其他设置保留位置。在途旧单继续核对交付，但轮转重设后确认失败的旧单不占新轮次。

分组接口在既有 `/admin/accounts/refill` 及其动作接口添加 `group_id` 查询参数；省略时兼容原规则。新规则存储在独立 settings 键，所有规则与旧版共用同一个 PostgreSQL advisory lock，无数据库结构迁移。回滚前应先停用新增分组的自动规则并处理其在途订单；旧程序只处理原规则。

## 未分配账号刷新

未分配到任何分组、状态正常、具有 refresh token 的 OpenAI OAuth 账号，默认每 15 秒扫描一次；启动时立即扫描。刷新成功后查询并保存额度，不自动分配分组或改变账号预设。已分组、影子、PAT、Agent Identity、已到期自动暂停或处于临时冷却的账号跳过。沿用共享的令牌锁、限流、并发限制和失败退避；大号池或慢请求时实际完成时间可能超过一个扫描周期。`TOKEN_REFRESH_UNGROUPED_CHECK_INTERVAL_SECONDS=0` 可关闭。

## 使用入口

- 账号管理 → 补号规则：连接与分组、补号规则、推送设置、手动补号、企业微信通知、消费与进度。账号列表也提供独立“手动补号”入口。
- 快乐首字 → 按分组单独设置：勾选 OpenAI 分组，独立设置开关和等待区间，取消勾选恢复全局默认。

补号默认只监测，不自动购买。接管补号时先停用号商原有自动补号，再开启本功能。配置中的 API Key 留空表示保留；替换时校验号商账户身份。有在途订单时只能更换同一号商账户的 Key，避免幂等键换账户后失去去重作用。

“并发与额度”根据健康储备、账号真实租期、5h/7d 剩余额度和当前并发计算缺口。每秒独立采样，利用率连续达到目标并满观察时长才允许按并发扩容；低于目标、采样失败、间隔超过 2 秒、配置变更或进程重启均重新计时。下单前再次读取负载，防止突发已结束后购买。检查间隔、冷却、在途上限和预算仍生效；只有最低健康储备不足可不经并发观察窗口补足。临期本身不授权购买，必须形成最低储备缺口或持续达标的并发缺口。“固定健康保有量”检查健康储备、临期和额度，剩余健康账号已满足最低数量时不补，不按并发扩容。“定时补号”按周期分批补入配置数量。

并发模式同时独立观察“账号退出预判”：有效 5h / 7d 剩余额度达到或低于该账号套餐下限（零下限关闭该窗口），或进入所设提前补号分钟数时，把该账号容量从预计容量扣除。仍保留分组内全部实际运行中请求，包括这些账号正在处理的请求；预判不会修改账号调度、并发设置、优先级或现有请求。多个账号同时满足条件时合并扣除，避免低估接续缺口。

例如两账号各 100 并发、当前共 90 个请求，一账号进入提前补号时间：当前利用率 45%，退出后预计为 90%。若目标为 85%，预计值持续达到目标并满既有观察时长后，可以提前补一个接续。已下单未交付的任务按其下单时保存的并发容量抵扣，跨组投递同样抵扣；已交付账号计入实际容量，避免针对同一缺口重复购买。预计剩余容量为零而仍有请求时算达标，无请求不按预判购买。最低健康储备不足仍按原规则独立补号。

当前与预计值分别显示、分别计时；预计退出的账号集合或其容量改变时重新观察，暂停、配置变更、失效采样和重启也清空观察窗口。最终预留预算前重新读取本地账号和并发，恢复额度、续租或在途交付已填平缺口时停止新增订单。限额按未来健康账号计数，允许临期或刚到额度下限的账号与接续账号短暂共存；现有上限、冷却、每日预算及订单幂等约束继续生效。

临期号可以继续调度，但不计入未来储备。在途任务抵扣缺口；即使保有量及上限均为 1，也允许临期号与替补号短暂共存。禁用、暂不可调度和低额度账号不算健康储备；影子账号不纳入计数。额度来自现有有效账号快照，未知或已重置/过时的额度不冒充准确数据，面板显示空值。

容量和固定储备模式按“账号 ID + 本次号商回收时间”保存临期接替关联，用于已获准订单的归属、失败重试和去重，不增加购买缺口、不覆盖下单原因。即使旧版本已保存尚未完成的临期记录，升级或重启后也必须重新满足当前规则：剩余最低健康储备充足且并发未持续达到门槛时不补号。退出预判关闭时，不因临期产生额外的预计并发订单。比如最低储备 1 个、并发目标 85%、观察 10 秒，扣除临期账号后仍有 65 并发容量、当前总负载 20，则不购买；总负载达到 56 且连续观察满 10 秒才按退出预判补号。

接替关联随预算和订单一起保存，确认失败后保留原套餐，只有当前规则仍有缺口才重补；导入成功后记录完成。完成记录独立于普通订单历史裁剪，同一次租期的关联在重启和多分组间共享。已有在途或窗口内购买的已交付订单可关联，一笔订单在一个池内只能覆盖一次租期；跨组投递的失败重试由原下单规则处理。进入窗口后保存的关联可跨越原账号到期或异常状态，但不会据此强制购买；账号续租、删除或移出分组会撤销旧租期关联。订单备注同时保存实际授权的最低储备或并发依据，以及接替账号 ID 和号商回收时间。定时模式不额外创建临期订单。

北京时间运行窗口支持跨午夜。暂停监测或关闭自动购买不会丢弃已受理订单；暂停推送会停止普通和超时保底新单，已完成的交付等待恢复推送；独立的每日定时强制补号仍按时创建新单。正在执行的订单使用下单时的投递配置快照。

## Codex namespace 兼容设置

“推送设置”提供与账号编辑页相同的“摊平 Codex namespace 工具（兼容）”开关，按分组独立保存，旧规则默认关闭。仅在兼容上游不接受 namespace 工具声明时开启：它会把命名空间工具改成 `namespace__tool`，可能导致依赖 `functions.<命名空间>.<工具>` 的调用失效。正常 Codex 上游应保持关闭；compact 压缩请求继续使用原有摊平行为，实际走原生 WSv2 的请求继续保留 namespace。

自动和手动补号均按下单时的推送配置快照设置新账号；修改规则不追改已有账号或在途订单。旧页面保存其他设置时省略此字段，会保留已经保存的选择。手动补号确认区显示当前保存的开关状态。

## 导入过期时间

推送设置的随机代理只从未绑定账号的有效代理中分配，每个代理最多由二开自动分配给一个未删除账号。选择和创建账号在同一个事务内，与受限管理 Key 的随机/最空闲分配互斥。没有空闲代理时，原订单保留为导入失败，可在添加代理或释放绑定后重试，不自动改为直连；新增补号仍需通过代理可用性检查。原生账号推送及显式指定代理保持兼容，已有绑定不自动重排。

从 `0.2.19-yoshub.native-expiry.1` 起，账号编辑中的原生 `expires_at` 保存实际暂停时间。OpenAI OAuth 账号导入时独立记录号商租期，再将导入截止（或更早的号商租期）加保留分钟数写入原生过期字段。调度、SQL 过滤、容量统计和自动暂停直接使用该值，不再重复加宽限；OAuth token 的有效期不变。

账号编辑 → 过期时间 → 设置到期后保留时间：保存 0–1440 分钟会从原始截止重新计算一次，并更新编辑框。直接修改过期时间按填写值生效，后续租期同步或网站原样回写不覆盖人工设置；再次保存保留分钟数则重新计算。已暂停账号不会自动恢复。提前补号仍依据号商回收时间，不包含保留时长。

网站推号兼容绑定导入 Key 与其导入账号：旧版 Key 使用逻辑标识 `legacy`，受限 Key 使用稳定 Key ID（轮换不改变身份），不保存密钥明文。该 Key 在详情、完整/精简列表、更新响应及导出中读到原交付时间；JWT 后台和其他 Key 读到实际原生过期时间。原样回传交付时间不会累加保留时长或覆盖人工截止，修改交付时间时只计算一次。兼容视图不用于网关调度及内置补号；权限、分组、调度开关和优先级使用原流程。

租期、保留时长、Key 绑定及截止模式不进入原生 `extra` 响应和导出。到期策略和原生时间在同一行锁事务内保存并写入调度 outbox；普通编辑、批量 extra 更新和旧快照上的令牌刷新不清除或覆盖受管元数据。JWT 备份还原保持导出的实际原生到期时间。

旧版账号转换前继续支持内部宽限，精简调度快照保留所需字段。数据转换将此前有效截止写入原生字段，不重复延长，保留租期与调度状态；外置旧账号仅在审计能确认导入 Key 时建立绑定，未知来源留待核对。

## 按套餐设置额度下限

补号规则保留通用 5h / 7d 下限，并可分别为 Pro5x 和 Pro20x 启用独立百分比（0–100，支持小数）。关闭某套餐覆盖或无法识别套餐时使用通用值；旧配置不启用覆盖，行为不变。设置随各分组规则独立保存。

每个被检测账号按自己的套餐匹配，优先使用购买套餐记录或关联订单，再识别账号 `plan_type`（pro5/pro5x/prolite 对应 Pro5x，pro20/pro20x/pro/chatgptpro 对应 Pro20x）。不会用下一次购买的套餐套用整个池。任一有效额度窗口的剩余百分比低于该账号下限时不计入健康储备；零下限关闭该窗口的低额度触发，未知/过时额度不伪装成低余额。套餐轮转顺序保持原设置。

新订单的补号备注记录实际采用的套餐阈值，评估列表显示匹配套餐和下限。新导入 API 账号保存购买套餐，已有订单也可识别。

## 真实租期同步

公开 Key API 的 `GET /api/customer/developer/v1/refills/{id}` 返回 API 订单的 `expires_at`，不能读取网站创建的订单。网站订单在该接口实测返回 `404 API order not found`；网站的客户状态接口要求登录会话，Bearer Key 不能替代会话。

本功能每 5 分钟轮询最多 5 个已导入 API 订单，轮转检查，手动“同步余额、租期与规则”也会检查；自动监测关闭时只由手动检查触发。先验证本地订单与账号关联，再原子更新私有租期元数据。失败、404、无效响应保留旧租期；429 遵守退避。网站推送账号使用导入时记录的租期，仍保留的旧版原始租期标记也可识别。面板明确区分“号商 API”“导入租期记录”“本地设置 · 未识别号商租期”，不把手动到期日期冒充号商数据。

## 钱包、密钥和任务

顶部展示总余额、冻结积分、可用积分及更新时间。旧钱包 API 的金额除以 100 换算积分；补号报价直接使用积分，保留小数。API Key 只保存加密值，响应不返回明文；从号商 Key 列表匹配有效期，面板显示北京时间到期时间和剩余天数。接口无法返回时显示未知。

任务展示提交、排队、处理、人工核对、等待交付、推送暂停、导入、成功及失败等真实状态和耗时，不推测百分比或预计完成时间。每日预算按北京时间归属到提交日，仅统计本功能的订单；钱包余额包含其他消费。在途预占属于提交当日，不跨天重复计费。

“消费与进度”按每页 10 条展示当前分组任务，支持页码和前后翻页；15 秒自动刷新保留当前页，切换分组或重新打开回到第一页。每条任务显示下单原因，新订单另保存下单前最终评估的备注：定时周期、并发数/利用率/阈值/观察时长，或最低储备缺口及临期、已到期、低额度、不可调度数量。原因和备注随订单持久化，重试或修改规则不改写历史；旧订单显示已保存原因，缺失时明确提示，不用当前状态反推。现有历史保留上限不变。

## 重试和一致性

已受理订单的状态查询固定在本次请求结束后 20 秒再查，包括正常等待、网络断连、超时及 5xx；成功或失败的累计查询次数不再延长此间隔。继续核对原订单，不因查询失败重新下单。号商明确返回更长的 `Retry-After` 时仍遵守，认证拒绝和人工阻塞处理不变。待交付查询和 Muze 原订单只读核对使用相同间隔；首次下单重试、钱包/报价刷新、已导入订单租期同步及超时保底购买保留各自规则。后台通常每 5 秒扫描一次，慢请求、订单积压或跨规则处理可能延后实际执行；25 秒请求超时后再等 20 秒，不会立即重发。

补号面板、原任务与同套餐替补任务的日志引用、通知及交付文件名统一使用号商任务 ID。号商尚未返回 ID 时显示“号商暂未返回 ID”；历史日志在读取时按任务关联解析为号商 ID，已清理且无法解析的历史关联明确显示不可用。内部任务 ID 仅用于幂等、关联与操作接口，不作为展示编号，不改写历史订单数据。

自动订单收到号商明确的 `failed` 状态后，释放原预算预占，并记住原套餐。“补号规则”中的“失败后立即补 1 个”勾选项按分组保存，默认开启以兼容已有规则；开启时立即重新评估需求，跳过普通检查间隔和下单冷却，仍有缺口时单次重补 1 个同套餐账号。关闭时保留同套餐重补和定时模式归还名额，但按普通检测间隔及下单冷却处理。冷却从上一次下单起算，不从确认失败起算；两项都设为 5 秒也不代表失败后固定等待 5 秒，条件已经到期时可在确认失败的同一轮补号。号商状态查询按下述固定间隔处理。

重补不额外增加需求，不再次推进套餐轮转。原失败任务与新任务互相记录关联，新订单使用新的幂等键、最新报价和当前推送设置；超时或响应不明先沿用已有订单核对；达到保底超时条件时可独立补一单。替补再被明确判失败时继续按同样规则处理，仍累计每日提交次数。旧客户端省略新的 `immediate_failure_retry` 字段时保留已保存的选择，关闭后不会因旧页面保存其他字段而重新开启。

同套餐重补仍受自动购买、监测、推送、时段、号商限流退避、在途、健康上限、单价及每日预算限制，下单前再次读取账号及在途容量。普通新增订单继续遵守配置的下单冷却。普通及临期订单的实际缺口消失时均暂停购买，保留原套餐轮次和接替关联；恢复并发需求后重新满足完整观察窗口才继续，最低储备不足仍可直接补足。定时模式只归还失败订单原来占用的一个周期名额。失败订单保留提交次数，释放积分只做一次；关联记录和新预算一起持久化，重启或多实例不会另开一路重复下单。只处理运行中收到的新失败结果，不追补历史终态失败，也不自动重下手动订单。`review`、拒绝待核对、交付导入失败仍按原流程处理。

1. PostgreSQL session advisory lock 串行化所有实例的配置及调度。
2. 先持久化订单 UUID、固定报价版本、配置快照和预算预占，再调用付费接口。
3. 网络超时/5xx 沿用原幂等键和请求体。重启从持久化任务继续；429 遵守 Retry-After。
4. 号商 `review`、拒绝待核对和导入失败仅在订单未超过配置的超时时间时阻止普通新增订单；启用超时重试后，超时旧单自动退出阻塞和在途判断。强制手动补号和每日定时强制补号可直接绕过阻塞。只有确认失败后才释放本地积分预占，提交次数保留。
5. 新账号先停用并禁止调度，写入恢复标记，完成分组和推送设置后才启用。创建后中断通过标记找到原账号，避免重复导入。
6. “重试原任务”沿用原订单；收到报价冲突等拒绝且没有号商任务 ID 时，须先向号商核对没有订单/扣款，勾选确认后可释放本地预占，再按新报价重新评估。已受理和状态不确定的网络请求不能用该操作放弃。
7. 配置写入使用 revision 防止多页面覆盖。刷新进度不覆盖未保存的编辑。

保存配置遇到后台补号短暂占锁时，每 100 毫秒重试获取锁，最多等 30 秒；拿到锁后重新校验最新 revision。超时或关闭请求时停止等待，已经进入保存流程的请求不会自动重放。后台订单处理仍使用原有非阻塞锁和幂等键。发布镜像、切换路由和排空连接不应在外部长期持有补号 advisory lock，否则会同时阻断配置保存和在途订单处理。

本地测试使用替身 API 验证购买与交付流程。生产验收只读余额、报价、有效期及规则预览，不为测试购买账号。

## 管理 API

仅完整管理员可访问；受限管理 Key 不自动继承此能力。修改配置的请求体不进入审计日志。

| 方法与路径（均位于 `/api/v1/admin/accounts`） | 行为 |
| --- | --- |
| `GET /refill` | 读取脱敏配置、钱包、报价、评估、任务 |
| `PUT /refill` | 保存 `{config, api_token, revision, wecom_webhook}`；Key 和 Webhook 留空保留 |
| `POST /refill/check` | 检查已保存规则和号商元数据，不下单 |
| `POST /refill/manual` | `{request_id, plan, revision, force?}`；按保存的设置预留 1 个手动订单；`force: true` 使用新请求并忽略待核对和在途上限，由现有任务流程购买及导入 |
| `POST /refill/jobs/:job_id/retry` | 重新处理原任务 |
| `POST /refill/jobs/:job_id/dismiss` | 仅未返回供应商任务 ID 的拒绝请求；必须 `confirm_not_accepted: true` |
| `GET /refill/jobs/:job_id/delivery?group_id=...` | 下载当前分组原订单的完整 SUB2API 交付 JSON；沿用账号导出的 step-up 验证，不购买、不导入、不修改订单 |
| `GET /:id/expiry-grace` | 读取账号保留分钟及有效调度截止 |
| `PUT /:id/expiry-grace` | 保存 `{minutes: 0..1440}` 并原子更新实际原生过期时间 |

快乐首字设置在原接口中增加 `group_overrides` 数组，各项包含 `group_id`、`enabled`、`min_delay_ms`、`max_delay_ms`。省略该字段的旧客户端保留已有覆盖；显式空数组清除覆盖。请求按 API Key 所属分组匹配，不能用共享账号的全部分组推断。原有 SSE 协议范围、真实输出计时和错误处理保持一致。

## 手动补号、排序和套餐标识

### 号商状态与交付下载

按号商官方 [状态与计费文档](https://pro.llmrefund.com/console/developer/docs#states)（2026-11-02 核对）识别补号的 `queued`、`processing`、`succeeded`、`failed`、`review`。界面同时显示本地导入阶段、原始号商状态、公开说明和积分预占/结算/释放状态。退款接口的 `cancelled`、`account_status=banned`、`settlement` 不属于补号任务状态；未知状态保留原任务 ID、预占和查询，暂停普通新增购买；可通过强制手动、超时保底或每日定时补号继续购买。

“消费与进度”每条订单提供“下载 JSON”。仅 `succeeded` 且 `result_ready=true`、租期未结束可下载；后端再查询原订单核对类型和就绪情况，只读获取 `/v1/refills/{id}/delivery`。保留交付的 `type`、`version`、`proxies`、账号凭据、`extra` 等原始字段和数值，账号 JSON 不写入补号状态、不进入缓存。下载异常只显示错误，不保存错误响应。

导入和下载同时校验交付类型、版本、单个 OpenAI OAuth 账号及非空凭据；不兼容类型或版本继续处理原任务；新增购买依照强制、超时保底或每日定时规则。浏览器保存前也校验内容，防止代理返回 HTTP 200 HTML 或错误对象时保存成 JSON。下载收到 `429` 后仅将退避时间合并到当前规则最新状态，重复点击和重启后仍遵守退避，不覆盖订单进度。恢复导入时优先核对已创建的本地账号；即使任务结果尚未落盘时租期结束，也不会把已提交的导入误报为未交付。

交付读取 `409` 按尚未就绪处理，`429` 遵循 `Retry-After`，网络异常或 `5xx` 稍后继续查原单；`410` 或明确租期结束记为交付过期，已成功订单不退还本地积分预算。`401/402/403/404/413/422` 明确显示原因、等待处理原任务。只有任务状态 `failed` 才执行已确认失败的预算释放和自动重补。

手动补号每次选 Pro5x 或 Pro20x 购买 1 个，完整继承保存的并发、分组、代理、优先级、倍率、WS、指纹、保留时间、状态、模板和模型映射。不会更改自动规则的套餐或开关；自动补号或监测关闭时仍可使用，绕过自动需求、时段和冷却，保留推送开关、配置版本、预算、单价、在途数量和代理容量检查。页面有未保存规则时先保存。

请求标识由毫秒时间戳和 UUID v4 组成，以冒号分隔，24 小时内可重试。浏览器会话保存未确认的请求，超时或重新打开弹窗仍复用它。后端在跨实例锁内持久化预算和任务配置快照，并为请求派生固定订单 UUID；24 小时内的手动回执不受 200 条普通历史限制，过期标识拒绝新下单。重试不会因为配置已修改而重复购买。

“强制补号（新购 1 个）”每次生成新请求，可在原手动请求结果不明或号商人工核对时直接再买一单，绕过待核对阻塞和在途上限。强制请求自身超时后，普通“重试确认原请求”仍复用该强制请求，重开弹窗也不会自动再买。明确拒绝的 HTTP 400/401/403 按共享 API 客户端的 `status` 字段清除待确认状态，避免错误锁住页面。强制补号仍校验推送配置、密钥、限流退避、单价、每日预算、余额及代理容量；旧单保留原状态和预算，可能仍交付并计费。

### 可配置的超时放行与保底补号

每个分组的 `timeout_retry_enabled` 默认开启，`timeout_retry_minutes` 默认 10，允许 1–1440 的整数分钟；旧配置自动使用默认值，旧客户端省略字段时保留已保存设置。必须同时开启自动补号、监测和推送才会自动购买。

每个未完成订单从创建起独立计时；超过设定时间仍未导入，立即退出补号需求、在途数量、在途容量和待核对阻塞判断。覆盖 `review`、提交结果不明、排队、处理中、交付等待、导入失败等所有未完成状态；共享投递分组的超时订单也按当前组配置排除。查询、状态变化和新订单均不会重置旧单计时。普通自动补号按最低储备、并发和定时规则继续运行，不必等健康储备为 0，也不必等待旧单处理。未超时新单仍正常抵扣缺口并遵守在途上限。

健康储备为 0、最新在途订单也超时的额外保底仍保留：按该订单套餐再买 1 个账号；新单继续卡住则到自己的超时时间后再补。新单只会影响这项保底的等待，不会阻止其他旧单退出普通补号判断。跨实例仍在同一锁内预留预算。

保底补单忽略待核对阻塞、在途上限、普通冷却、自动时段和定时周期名额，不推进套餐轮转；最长监测周期不会延后已经到期的本组订单检查。下单前重新读取号池，防止报价查询期间已恢复储备仍继续购买。余额、每日预算、单价、推送配置及号商限流退避继续生效。

超时本身不代表号商确认失败：原订单保持查询和交付处理，积分预占不释放，新旧单可能均交付并计费。新订单优先于超时旧单推进交付，避免旧单积压拖慢导入。保底新单记录 `timeout_retry_of` 关联，普通新增按原规则推进套餐轮转；已退出需求判断的旧单后续确认失败只释放其预算，不再重复安排另一份失败重补，也不归还旧的定时周期名额。超时和强制补号创建新订单，和“重试原任务”核对原订单分别处理。

“查看 / 调整内部排序”中的“一键恢复全部自动排序”跨全部分组、状态和分页清除手动排序覆盖；原生 priority 字段保留。账号标识将号商 pro5/pro5x 映射到紫色 Pro 100，pro20/pro20x 映射到 Pro 200，仅调整 OpenAI 显示，不改凭据或供应商套餐参数。

## 每日固定时间强制补号

补号规则中的独立选项 `daily_schedule` 设置 `enabled`、`time`（北京时间 HH:mm）、`quantity`（1–100）。默认关闭，界面初始时间 08:00、数量 1。开启或修改时间只安排未来的执行；仅修改数量或其他设置不推迟已有时刻。每个北京时间自然日最多一批，已执行当天即使重新开关或改时间也不再购买。

到点按配置套餐或轮转顺序一次性持久化指定数量的新任务及预算，然后由原任务执行器逐个提交。无论健康储备、待人工核对、在途上限、普通冷却、补号时间窗口如何，均可创建该批任务；与自动购买及监测开关独立。推送暂停时仍购买，交付等待推送恢复。定时批次不占普通周期名额，不触发额外的确认失败重补；超时保底规则仍可按缺口另行工作。

密钥、单价上限、每日数量/积分预算、可用余额和代理配置继续校验；不足以创建整批时保留待执行状态，每分钟尝试，页面显示阻塞原因。执行记录与全部任务、轮转位置和预算在共享锁内原子保存，重启或多实例不重复。停机跨越多日只补最近已到点的一批，不累积所有漏掉日期的订单。已创建的批次不因关掉定时选项而取消。

## 企业微信通知

配置指定群机器人的官方 Webhook，地址加密保存、响应不回显且配置请求体不进入审计日志。“补号进度通知”和“积分不足 / 低余额”分别有开关，默认关闭；默认预警阈值 100 积分，可设置 0–10000000。沿用已有开始补号通知开关，覆盖开始、确认失败，以及1208 和 Muze 自动、手动补号的成功导入和 5 分钟未导入提醒，不需要重新配置机器人。

开始处理自动或手动订单时发送套餐、积分、并发、分组 ID、任务号和时间。余额通知每分钟读取号商钱包，不依赖自动购买或监测开关；达到阈值或下单前积分不足时通知，持续不足不重复提醒，恢复后重新触发。页面读取评估不会触发钱包查询。

消息采用与 NewAPI 相同的企业微信 text 格式，校验 HTTP 和 errcode。发送限时 5 秒，失败不取消订单，面板展示通知状态。企业微信无幂等键，订单生命周期通知持久化发送标记后只尝试一次；超时重试提醒独立保存内容和重试时间，发送失败至少 5 分钟后重试，不阻塞购买。发送超时可能无法确认送达，重发可能产生重复通知。关闭通知不会取消在途补号。

自动或手动订单收到明确 `failed` 结果时，通知套餐、积分、分组、原任务、号商任务及后续处理方式。自动单说明仍有缺口并满足既有条件才重补原套餐；手动单提示按需手动处理。每个订单的失败通知独立记录发送尝试，重启及重复轮询不重复提醒；重补订单再次失败会有自己的提醒。历史已结束的失败任务不补发通知，超时和待核对不冒充确认失败。

1208 和 Muze 的自动、手动订单真正进入 `imported` 且已有账号 ID 后发送成功通知；号商 `succeeded` 但还在等待交付或导入时不提前报成功。从本地下单时间起满 5 分钟仍未导入的订单，在后台本轮交付处理后提醒一次，包含当前状态、补号方式、套餐、分组、原号商任务号和等待时长。同一轮已成功导入、已结束，或已导入但等待恢复推送的账号不会报未导入超时。后台通常每 5 秒检查一次，规则按保存的检测间隔和下单冷却决定是否检查需求或购买，已受理订单在每次查询结束后至少间隔 20 秒再查；慢请求或多规则可能延后实际处理。提醒不受普通下单冷却、检查间隔、自动购买/监测/推送暂停或号商退避影响，这项固定 5 分钟提醒本身不下单；另行启用的可配置超时保底规则可创建新订单。提醒后成功导入仍会收到成功通知。两种通知各自持久化去重，重启不重复提醒；终态历史订单不追发成功或超时通知。

达到配置的订单超时时间时，`timeout_retry_notify` 默认开启，独立于进度通知开关和健康储备数量，使用本组已保存的机器人，发送原任务、状态、等待时间、阈值和自动补号处理结果。预算、余额、密钥或限流阻止新单时也会提醒；每个超时订单持久化去重，新单再次超时会再次提醒。失败通知内容持久化，至少 5 分钟后重试，后续提醒不会覆盖未送达内容，购买不等待机器人恢复。未配置 Webhook 时页面仍显示补号状态。

## 本地账号评估与额度一致性

“消费与进度”每 15 秒 GET 本地状态，即使号商检查或手动补号请求仍在等待也继续刷新。GET 不获取任务锁，不调用号商、额度探针或上游；直接从 Sub2 数据库的账号及 codex 5h/7d 快照、Redis 并发重算评估。局部读取最长 3 秒，失败明确显示错误，不把旧表冒充实时数据。缺失、无效或已重置窗口的额度显示未知。订单处理、独立的后台钱包通知检查及号商租期同步按各自周期访问外部接口，不与页面评估刷新绑定。

自动下单在号商报价 / 身份请求完成后再次读取本地需求，避免慢请求期间额度或账号状态已改变仍按旧缺口购买。主动额度探针的结果先完成本地持久化再返回页面，修复先显示新值、随即读回旧值的窗口；补号 GET 也不再复用 settings 中落后的评估结果。并未强行把额度设为单调下降，真实重置或新的上游有效观测仍正常显示。
