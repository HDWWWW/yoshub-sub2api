# 1208 与 Muze 补号

在账号管理里打开「补号规则」，选择分组后设置「本分组自动补号的主号商」并保存。新分组默认使用 1208。启用「自动备用补号」后，另一个号商负责备用。手动入口分别为「1208 手动补号」和「Muze 手动补号」，1208 按档位选择，Muze 按号商返回的商品名称选择。

| 分组主号商 | 普通自动补号和每日定时任务 | 开启备用后的号商与套餐 |
| --- | --- | --- |
| 1208 | 1208，按所选套餐扣积分 | Muze，1 个可下单的 Pro20x 商品，使用预购次数 |
| Muze | Muze，按所选套餐使用预购次数 | 1208，1 个 Pro20x，按报价值预占积分 |

## 备用和订单归属

- 普通自动补号连续确认失败，或普通自动订单等待导入超时且分组仍有需求时，创建一笔备用单。默认阈值为 3 次、5 分钟。希望第一次明确失败就切换，可设置为 1 次。手动及每日定时订单按提交时指定的号商处理。
- 主号商确认所选套餐无库存、无次数或积分不足时，也按该分组的次数或持续时间阈值处理。跨组在途订单的本地预占和单次网络错误单独处理。购买前重新核对缺口、分组、代理和当日预算，并保存购买记录。
- 备用单覆盖的原任务有独立的订单号，同批触发只创建一笔备用。原任务可能迟到并计费。切换主号商只影响新购买，已有订单的查询、推送和租期同步由接单号商继续处理。
- 每日定时任务先预占整批套餐。备用单沿用本分组已保存的 Pro20x 并发、推送分组、代理、优先级及租期设置。1208 使用积分，Muze 检查套餐剩余次数和当前库存，两者共用分组每日购买数量上限。

## Muze 连接和交付

Muze 设置使用服务器端加密的 API Key。已有和新建的规则可使用安装时提供的默认密钥。需使用独立余额的分组可在「Muze 手动补号 → Muze 连接设置」保存自己的密钥。留空密钥保留已配置值。推送连接须指向本 Sub2 实例，留空连接 ID 会选择 Muze 已启用的默认 Sub2API 连接。每笔订单保存实际连接 ID 和目标分组。

打开「Muze 手动补号」会读取 `GET /api/my/products`，也可点「刷新商品列表」更新。列表按号商的商品 ID 和名称分别展示普通版、V2 及新上架商品。库存来自 `cardStock`，同一档位各版本共用 `remaining` 次数。暂停、过期和次数用完的商品也可查看。新档位或未识别的购买模式显示原因，待规则支持后可购买。

手动补号使用选定的商品 ID。普通自动、每日定时和备用补号按规则档位选品，同档普通版可用时优先，随后依次考虑号商列表中可用的版本。每次购买都复核库存、配额和目标连接，扣除本地在途预占。V2 沿用对应 Pro5x 或 Pro20x 档位的并发和阈值。

下单前保存商品 ID、购买模式及 `GET /api/my/connections` 核对过的目标连接。每次 `POST /api/my/orders` 购买 1 个，普通版携带本次请求的 `requestId`。普通版回执丢失后按此编号查询。V2 使用工作室接口的单笔回执，结果不确定时保留预占，管理员可在「消费与进度」输入号商「我的订单」中的原订单号核对。结果待确认的 V2 原单须核对后才可触发超时补购。

核对到 `pushStatus=pushed` 后优先使用明确给出的 Sub2 账号行号，否则使用目标分组、上游 `oauth.accountId`、邮箱和创建时间核对本地账号。多个候选时交给管理员核对。账号交付后可从账号列表导出。

## Muze 剩余次数提醒

在「补号规则 → 通知」打开「Muze 剩余次数不足提醒」，勾选要监测的商品，填写次数阈值并保存。新开关默认关闭。可将阈值设为 0，只在次数用完时提醒。后台约每 5 分钟读取已配置分组的商品目录，关闭自动补号时也会检查。

当选中商品的 `remaining` 等于或低于阈值时，系统通过本分组配置的企业微信或 QQ 发送提醒。普通版和 V2 共用同档次数，每档提醒一次。次数恢复到阈值以上后，再次降至阈值会重新提醒。目录读取失败或商品暂时下架时，系统保留原提醒状态。

## 号商预计回收时间

Muze 订单的 `refundDueAt` 在订单进度和账号列表中显示为「号商预计回收时间（北京时间）」。例如 `2026-11-24T16:15:00Z` 显示为 `2026-11-25 00:15:00`。缺少有效时间时，界面显示等待同步。系统按本地租期策略计算实际到期时间，并单独展示。后续取得号商时间会自动更新，保留管理员设定的截止时间。

订单进度另列 `refundPhase`。其中 `returned` 表示号商已退回购买次数。

## 从粉嘟嘟升级

保留原分组的备用开关、阈值、已触发的任务关联及历史订单。旧号商的密钥、推送连接和待确认请求专属于原号商。历史订单保留原来源与已有时间。在途旧单可在原号商核对后，通过「消费与进度」归档。浏览器里待确认的旧请求单独归档。

升级所有执行补号的实例后启用新号商规则，避免旧版 worker 回写不认识的字段。设置、请求日志和配置导出应遵守现有密钥脱敏规则。
