# SmartWS

SmartWS changes the upstream transport for eligible Responses requests. Clients keep the existing HTTP JSON/SSE interface. Native WebSocket ingress remains a separate path. This checkout runs one Go application with an embedded Vue frontend; scheduling, forwarding, and usage recording are internal services, not separate Core, Relay, or Worker deployments.

## Routing and controls

`internal/server/routes/gateway.go` registers HTTP POST and WebSocket GET `/v1/responses`. Both retain the existing authentication, group permissions, concurrency controls, and `OpenAIGatewayHandler` scheduling. HTTP forwarding selects its account first, builds its normal upstream request, then `doOpenAIUpstream` optionally calls `doOpenAIHTTPOverWS`. Existing response handlers still format SSE/JSON, and `RecordUsage` retains billing ownership. Converted Chat Completions uses the same adapter when its selected upstream is Responses.

The admin group field `smart_ws_mode` accepts `enabled`, `disabled`, and `inherit`. `enabled` opts HTTP requests into SmartWS; both other values retain HTTP upstream. Set it through the group editor or `PUT /api/v1/admin/groups/{id}`. Changes invalidate the existing API-key authorization cache. Migration 254 is additive and defaults existing groups to `inherit`; rollback binaries ignore the new column.

Global WS enablement, credential-type enablement, account/global force-HTTP, and plugin routing retain precedence. Compact, Messages, Excel OAuth, and plugin-dispatched requests are excluded. A custom API-key endpoint also needs the account's existing explicit WS opt-in; OpenAI compatibility alone is insufficient. Group SmartWS controls HTTP adaptation, while native WS continues to use the existing account ingress settings.

Native connections reauthorize every subsequent generation through the same API-key cache and access rules as HTTP: key/user/group status, IP restrictions, group membership and current model allowlists. Each turn uses current user concurrency, pricing, monetary limits and normal billing/RPM admission. The first turn is counted once; simple-mode billing exemptions remain unchanged. Key reassignment or a change to connection-bound protocol/routing policy requires a reconnect. Authentication lookup failures stop before dispatch instead of retaining stale authorization. Subscription identity and windows are rechecked through the existing subscription service, so a replaced subscription cannot be charged through the old connection. Each turn retains its own immutable usage/pricing snapshot.

## Protocol and dispatch

The [OpenAI WebSocket mode guide](https://developers.openai.com/api/docs/guides/websocket-mode) specifies `wss://api.openai.com/v1/responses` and `response.create`. API-key payloads omit HTTP-only `stream`/`background`. OAuth uses this repository's existing Codex endpoint `wss://chatgpt.com/backend-api/codex/responses` and Codex payload conventions; actual OAuth support must be validated against the intended account and deployment before enabling traffic. The adapter retains finalized upstream authentication/session/capability headers and adds the existing Responses WS beta only when none is already selected.

The complete finalized input, instructions, model, effort, tier, tools, tool results and encrypted reasoning pass into the adapter. HTTP requests carrying previous_response_id or conversation are excluded from the independent pool; native WS retains its existing continuation path. Existing account/group policy still applies before transport selection. SmartWS does not reduce context or reasoning effort. OpenAI native forwarding does not remove a client continuation ID or synthesize replacement full context after a connection failure. It sends no extra probe generation.

OpenAI OAuth-like accounts normalize input message roles from `system` to `developer` before dispatch, including HTTP passthrough, native WS first/subsequent turns and the large-request HTTP bridge. This narrow compatibility step preserves message order/content, existing `instructions`, continuation IDs and tool/encrypted history. API-key and other-provider requests are unchanged. It does not retry a rejected request: an HTTP bridge can itself return a validation error, and changing transport cannot guarantee that the upstream will accept the request.

Dispatch states are `NotSent → MayBeSent → Received → Terminal`. `MayBeSent` is set **before** attempting a write. Only a failure before dispatch may use HTTP fallback. Oversized/background requests, unsupported WS handshakes, and pre-dispatch network/capacity failures preserve the complete HTTP body. Handshake authentication, rate-limit, and other explicit upstream errors retain their status/body. No permanent negative capability cache is used.

After a write may have occurred, native WS retains the no-replay boundary. Eligible HTTP requests with complete input can return a pre-output transport failure to the existing bounded retry policy. This is allowed only before client output, delivered failure, observed usage, tool execution, policy refusal or continuation dependence closes the recovery window. It does not prove that the upstream did no work. Explicit pre-acceptance rate-limit or temporary rejection signals follow their separate bounded rules. Other uncertain outcomes remain failures; observed failed usage is retained for accounting. A bounded failed-event tail can collect authoritative usage after a bare error. Missing terminal usage is never fabricated as billable success.

This boundary also applies inside the HTTP client used for a pre-dispatch fallback or a native large-request bridge. These requests disable redirects and body recreation, so a 307/308 cannot dispatch the POST again and HTTP/2 cannot recreate an already-written body. A 3xx response is returned as a terminal upstream rejection with its status/body and without a Location header. Ordinary HTTP requests outside SmartWS keep their existing policy. The fallback response observer retains explicit JSON/SSE failures and observed usage with HTTP billing attribution, distinguishes incomplete results from success, and only collects a bounded matching failed tail (eight events, 200 ms). An explicit failure is not converted into an uncertain transport outcome.

HTTP adaptation exposes an unrecoverable uncertain transport outcome as `smart_ws_dispatch_uncertain`: HTTP 502 before output, or a protocol error event after SSE output has started. The message states that the request may have executed and was not replayed. No successful completion or `[DONE]` is synthesized for this failure. Explicit upstream terminal errors retain their original payload instead.

HTTP fallback validates each bounded SSE event before handing it to the formatter. EOF or `[DONE]` without a Responses terminal, and empty, truncated or nonterminal synchronous JSON, report the same uncertain outcome. Observed partial usage retains HTTP attribution. Non-streaming `background=true` requests may acknowledge a valid response ID with `queued` or `in_progress`; these increment `background_accepted`, separately from completed generations and their latency samples.

Both HTTP fallback and HTTP-to-WS adaptation retain observed usage when a later explicit failure has absent or zero usage. A nonzero terminal usage remains authoritative, including lower token totals; usage from a different response ID is never merged into the failed turn. The original error and transport attribution remain unchanged, and this accounting recovery does not dispatch another request.

Handshake provenance remains attached to errors through the HTTP formatter. An unstructured or request-scoped 403 is an endpoint rejection, not evidence that the account credential is invalid; it does not increment account 403 strikes, cool down shared groups, or disable the account. A 401 or structured credential/workspace revocation retains the existing authentication policy. Explicit 429/529 signals retain the bounded rate/overload policy. Failure classification and retry limits remain authoritative; a generic rejection is not permission to replay.

Native `ctx_pool` and `passthrough` ingress also deliver explicit handshake errors before closing, including the upstream error object, HTTP status, and `Retry-After` hint. An endpoint rejection does not lower the shared account's scheduling score. A real 401 still applies the existing credential protection; clearing an error alone does not re-enable a disabled account.

For native clients, a turn that loses its upstream connection before a terminal event receives `smart_ws_dispatch_uncertain`, including when earlier turns on the same connection completed. Dispatch and delivered-error state reset between turns. The large-request HTTP bridge uses the same no-replay rule: it retains continuation IDs and encrypted reasoning, returns validation errors without deleting fields and resending, and records observed failed usage. A bare error can collect at most eight matching tail frames within 200 milliseconds for authoritative failed usage; a later completion cannot overwrite that error.

An endpoint 403 or unsupported-WS status pauses HTTP-to-WS attempts for the same account, credential, destination, proxy, and capability/identity headers for 30 seconds by default. Later independent requests may choose HTTP before dispatch; cache hits do not extend the pause. Authentication changes do not inherit the old pause. Session IDs are excluded from this rejection cache only; connection reuse isolation remains unchanged. This bounded process-local cache does not affect native WS. HTTP continuation requests are excluded from the independent pool, and native continuation ownership is preserved.

## v0.2.22 compatibility

The upstream release does not change the WS handshake, response.create envelope, connection-pool protocol or WS library versions. Its shared SSE and compatibility fixes are integrated with the custom dispatch and accounting rules. A JSON keepalive can precede response.created without establishing ownership. On a reused independent socket, a control frame tagged with the previous response ID is skipped before delivery, usage accounting or retry decisions. Unattributed work or usage in a control frame, including in a failure tail, cannot be charged to the current turn or used to authorize a replay. An identified current turn retains its own reported usage. Unexpected lifecycle frames and mismatched IDs still fail validation.

The independent SmartWS pool shares the HTTP dialer's TCP liveness policy (15 s idle, 5 s between probes, 3 probes; best-effort TCP_USER_TIMEOUT of 30 s on Linux). This detects an unresponsive TCP peer, which on a proxied route is the proxy. It is not a 30-second model timeout: the WS handshake remains bounded at 5 seconds and the application read timeout defaults to 120 seconds. The separate native WS dialer is unchanged.

The independent pool reports `stale_frame_ignored` for discarded previous-turn frames and `unattributed_failure_tail` when a failure tail cannot authorize retry. Neither counter includes payloads or response IDs.

A successful upstream turn can return its socket to the pool when the last byte of the validated terminal event has been read. An SSE reader need not make an extra EOF read. A partial terminal, failure, cancellation before terminal consumption, or change of workspace does not grant reuse.

OpenAI passthrough does not treat a request-level `invalid_encrypted_content` as proof that a particular history item is bad: it neither applies cached invalid marks nor strips and resends the request. Ordinary non-passthrough OpenAI retains upstream's narrower recovery for reasoning and compaction items, not message ciphertext or opaque content parts. Encrypted output counts as work even before any visible text. Sealed tool calls reconstructed from delta frames keep the upstream ciphertext and encrypted-argument markers.

Keepalive and happy-first notifications are control output, not model progress. They must use the same serialized frame-writing path, preserve the configured happy-first deadline, and keep protocol errors in SSE once the response is committed. They do not extend the semantic first-output timeout or remove tool/usage/continuation restrictions on retry. The official Messages pre-content buffering applies to its HTTP bridge; it does not enable Messages in the independent SmartWS pool.

## Connection bounds

Each lease is serial. Reuse requires matching account, authorization, destination, proxy, protocol/capability/session headers, downstream API key, and execution scope. The identity capacity bucket excludes proxy/session/account aliases so duplicating an upstream credential cannot gain extra capacity. Credentials and header values never appear in SmartWS metrics.

Limits are process-local. Multiple app replicas each have their own pool; size the aggregate accordingly. The existing account scheduler still governs business concurrency. Configuration uses `gateway.openai_ws.*` or `GATEWAY_OPENAI_WS_*` environment variables:

| Key | Purpose |
| --- | --- |
| `max_conns_global`, `max_conns_per_account`, `max_conns_per_identity` | Connection ceilings; account auto-pool scaling also applies |
| `max_queued_global`, `max_queued_per_identity`, `queue_limit_per_conn` | Bounded acquisition/lease queues |
| `max_concurrent_handshakes`, `max_concurrent_handshakes_per_identity` | Concurrent handshake ceilings |
| `handshakes_per_second`, `handshakes_per_second_per_identity` | Handshake rate limits |
| `idle_timeout_seconds`, `max_conn_age_seconds` | Idle reclamation and maximum age between turns |
| `max_request_bytes`, `max_upstream_frame_bytes` | HTTP-to-WS request limit and incoming upstream WS message limit |
| `handshake_rejection_cooldown_seconds`, `max_handshake_rejections` | Temporary endpoint pause (1–300 seconds, default 30) and bounded entries (1–65536, default 1024) |

Defaults are conservative guardrails, not measured server capacity. HTTP requests above the WS size bound retain their entire body and use HTTP before dispatch. Existing HTTP and native-client body/frame limits remain additional bounds. Cancellation interrupts queued acquisition and active I/O; damaged or incomplete leases are evicted. Age/idle cleanup never cuts an active generation; an aged native session rejects the next turn before dispatch. HTTP adaptation opens connections on demand and does not create idle prewarm connections.

## Observation and release

`GET /api/v1/admin/ops/smart-ws` requires the existing admin/monitoring access. The Ops dashboard shows connections, active leases, acquisition/handshake counts and limits, reuse, fallback, queue rejection, cancellation, upstream terminal errors, transport failures, and uncertain dispatch. Counters are per process and reset on restart. Latency retains at most 256 successfully delivered samples, separates new/reused connections, and measures actual content rather than metadata or gateway notifications. These server-side counters do not establish end-to-end client success rates.

Native WS submits the first client-visible failure of each turn to the existing bounded asynchronous ops log queue immediately, without waiting for the connection to close. The entry snapshots that turn's model/account/error context; subsequent failure frames and connection cleanup do not duplicate it. The searchable message retains the upstream reason and known HTTP status. For a structured validation `detail`, only the reason is extracted, not the `input` field, even if the HTTP bridge serialized the validation array into a string. Monitoring filters, policy-specific logging and queue limits still apply; this does not add complete raw response bodies to logs or synchronously persist every error.

Handshake 401 and 403 have separate counters. Endpoint pauses, subsequent requests during pauses, and rejected continuations are separate from upstream terminal generation errors. Error events include `stage=ws_handshake`, the classification reason, account and proxy attribution, and the upstream host/path; no credentials or request/header dumps are added. `handshake_auth` remains a legacy combined 401/403 counter for API compatibility, not a credential-failure diagnosis.

System logs additionally index `component=service.openai_ws_handshake`, `message=smart_ws.handshake`. Each failed pool dial emits a warning. Successful dials emit an info record for the first success, each 64th success, and the next success anywhere in that process's pool after a failure. These are actual connection handshakes, not per-request or reuse logs. The existing bounded logging queue, logger sampling and configured log level still apply; pool counters remain the source for total counts. HTTP request IDs are inherited from the request context when available; background dials need not have a request ID.

The diagnostic records include status, elapsed time, account/proxy IDs, endpoint family, acquisition/handshake counts, and `dispatch_state=not_sent`. Request headers are summarized only by presence, byte length, count and HMAC; credentials, session identifiers, routing/turn-state values, proxy URLs, and request bodies are never copied into these records. HMAC keys are random and local to a pool, never persisted; compare only records with the same `fingerprint_scope`. Response summaries allow recognized server names, strictly validated request IDs/CF-Ray, parsed Retry-After, content type, a bounded observed-body fingerprint and kind, and allowlisted error code/type. Error messages and complete response bodies are excluded. `body_observed_bytes` is the body already retained by the dialer, which may be truncated; it is not the original response size. A Cloudflare content marker is evidence of that marker only, not proof of the reason for a refusal. The observer does not perform a retry, change headers, consume extra response data, or enable a group.

Validation must include isolated fault injection and actual upstream/entry checks. Compare fixed account, credential, model, reasoning effort, request, session, and concurrency; report HTTP, cold WS, and warm WS separately. Record client terminal outcomes, transport failures, upstream errors, and replay counts independently. Small samples establish protocol behavior, not site-wide capacity or latency improvement.

Release an immutable image through the discovered blue/green operator, with new groups initially using HTTP. Validate the standby before switching, enable a bounded canary, and drain old HTTP/WS connections naturally. Roll back transport with the group control and roll back the application with the operator's previous image. Do not restart PostgreSQL/Redis or force-stop streams. Verify the real proxy configuration supports Upgrade, streaming, and sufficient read timeouts; source templates alone are not evidence of the live configuration.

Every Nginx hop, including the containerized blue/green router, must set `underscores_in_headers on` to retain `session_id` and `conversation_id`. The host setting does not configure a separate router process. Align the router read timeout with the host and application (900 seconds in this deployment); a 120-second router timeout otherwise closes a quiet native session before the application's 300-second inter-turn deadline. Validate both header delivery and a silent upgraded connection through the actual proxy configuration. Apply router-only changes with `nginx -t` and a graceful reload; let existing workers drain without a forced shutdown.
